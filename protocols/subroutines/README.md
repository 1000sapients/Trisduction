# TRISDUCTION SUBROUTINE SKILLS · Scribe Orientation

This folder holds the nine Trisduction skill files as plain text. Each is a complete, self-contained instrument. This document exists so that a scribe arriving fresh knows three things before it does anything else: that these instruments exist as separate files, that a file being filed here does not mean it is loaded in the session, and where in this repository to look when the architect says read the git.

Assembled 2026-08-15. Sizes measured at assembly. Nothing here is authored content, the arrangement is the whole contribution, ΔM = 0.

---

## 1 · The first question a scribe asks

**Is the instrument loaded, or is it only filed here?** The two are different states and confusing them is the most common failure at session head.

A skill is **loaded** when its text is in the session and its triggers fire on shape. Check the available-skills list in the session. If the name appears there, the instrument is live and can be called by its trigger words with no further ceremony.

A skill is **filed** when it exists in this folder but is not in the session. Filed is not loaded. A filed instrument fires no trigger, and inventing its behaviour from this README's one-paragraph summary is a fabrication, not an execution. Two honest routes when the instrument is filed but not loaded: fetch the file text and run from the text, or tell the architect the instrument is not installed in this session and name it. Say which route you took in one line. Never silently improvise a substitute and never claim the instrument ran.

**When neither applies**, when a needed instrument is neither loaded nor filed, say so plainly and offer the nearest core route rather than approximating. A named gap is information the architect can act on. An unnamed approximation is a defect with a plausible face.

## 3 · How they interlock

Five layers, and the order is the discipline.

**Governance sits on top of every write.** `git-automation` gates the repository and `codex-hygiene` gates the corpus. Neither produces content. Both can stop a delivery, and a content skill never overrides either.

**Three decks produce the material.** `scripture-analysis` for corpus reading, `trisduction-subroutines` for the word, essay, figure, statecraft, etymology, phoneme and ebook instruments, `1000-sapients-subroutine` for the register. They share one engine and one warrant-typing law, so a claim carries the same grade whichever deck raised it.

**Two engines adjudicate.** `universal-cascade` issues verdicts on mathematical propositions and claimed proofs. `trisduction-audit-cycle` runs the adversarial pass against anything already built. The decks produce, these two judge, and the separation is deliberate: an instrument does not certify its own output.

**One skill renders.** `trisduction-publication-format` owns the deliverable, its architecture, its voice, and its visual contract. A content deck hands it finished material, never formatting decisions.

**One skill publishes the record.** `session-chronicle` turns the working session itself into a public artifact, and it pushes through the git gate like everything else.

Beneath all nine sit the platform document-creation skills, which are the actual file machinery. They are the hands. The nine here are the judgment.

## 4 · Precedence at session head

Consult the register of record before analysis. The Codex-First Law binds: where the codex already resolves a matter, the resolution is applied by reference and never re-derived, and a verdict issued without the consultation on a matter already resolved is void and re-runs.

Then, in order: hygiene before any build that touches identified entries, the deck for the material, the engines for the verdict, the format skill for the deliverable, the git gate for the write. A push runs only on an explicit yes and never on inference, including when the architect's own instruction appears to pre-authorize it. Conditional permission is not the yes; ask for it plainly and take the answer.

## 5 · Reading the git

When the architect says read the git, this is where to look.

**Three masters, folder-anchored and version-stamped.** The folder is the fixed identifier; the file inside carries the version. Resolve current by listing the folder, keeping the files matching the stem, parsing the version token, normalizing `.` and `_` alike, comparing as numeric tuples component by component and never as strings, and taking the highest. A `CURRENT.txt`, where present, is advisory and may be stale; it never overrides the highest version actually present.

| Master | Folder | Filename stem |
|---|---|---|
| Main Codex, the register of record | `master/` | `TRISDUCTION_Master_Codex_Unabridged*` |
| Theological PSP Codex | `Theological PSP Codex/` | `SCRIPTURAL_PSP_MASTER*` |
| System Role, the loaded role | `protocols/` | `TRISDUCTION_Unified_Master_System_Role*` |

**The ledger folders.** `psp/` holds one file per coordinate and `protocols/` one file per rule-module, filename equal to identifier, both census-tracked. `INDEX.md` is auto-generated from those two folders and is never hand-edited. `CODEX_DELETIONS.log` is the append-only removal manifest.

**The library.** `Publication Library/` holds every finished written document under a category, sub-area, topic path. Papers, essays, scripture readings and registers file there, not into the ledger folders.

**This folder.** `protocols/subroutines/` holds the nine skill files and this orientation. It is a subfolder, so the index builder, which lists one level and does not recurse, never sees it. Nothing here enters the census, and a hygiene reconciliation across a skill push shows zero delta by construction. That is intentional: a skill is tooling, not a coordinate, and flattening these files into `protocols/` would enrol nine tool documents into the rule-module ledger and corrupt the count.

**Fetching a file.** Raw reads need no credential on this public repository. The formula is `https://raw.githubusercontent.com/1000sapients/Trisduction/main/` followed by the path, with spaces percent-encoded. Directory listing needs the API and is rate-limited without authentication, so prefer a known path over a listing where the path is known.

## 6 · What is deliberately not here

**No credentials, ever.** No token, key, or secret enters this repository in any file, any example, or any commit message. The push tooling and its credential handling live outside this folder in a separate private skill, and that skill is not filed here and is not to be pushed here. A scribe that finds itself about to write a credential into a repository file has already made the error; the correct move is to stop and use the environment variable by reference.

**No private working material.** Session transcripts, drafts, and working notes are not filed here. `session-chronicle` governs what part of a working session becomes public and how.

**A scan was run before this folder was created.** Every file here was checked for credential patterns, contact data, personal identifiers, and local path leakage. The only credential-shaped strings present are the detection regexes inside the git governance skill's own secret scanner, which is where they belong. The only contact datum present is the author name and email in the publication skill's frontmatter defaults, which already appear on the face of every published preprint and are therefore public by prior act, not exposed by this push. Any scribe adding a file to this folder repeats that scan first.

## 7 · Versioning in this folder

Skill files follow the same append-only law as every other document in the repository. A revised skill is filed as a **new file with a bumped version**, never as an overwrite and never as a delete. The naming pattern is `<skill-name>_v<major>_<minor>_<patch>.md` and the resolve rule of section 5 applies: highest numeric tuple within the stem is authoritative.

**The suffix is a filing counter for this folder, not the instrument's own internal version.** Several instruments carry a revision history inside their own text that this counter does not track, so `_v1_0_0` means first filing here and nothing more. The standing example: `trisduction-publication-format_v1_0_0.md` is byte-identical to `publication/SKILL_trisduction-publication-format_v1_3_0.md`, where the older naming used the instrument's own version. The counter was chosen over the internal version because most instruments do not declare a machine-readable version, and a scheme that works for some and guesses for the rest is worse than one that is uniform and honestly labelled.

Patch for a small correction, minor for a new section or a new instrument inside an existing deck, major for a restructure. The previous version stays in place, which is what makes an interrupted or botched write incapable of destroying the current instrument.

The file installed in a session and the file filed here are the same text. Where they ever diverge, the installed copy is what actually executed and this copy is what is auditable; reconcile them rather than choosing, and record which way the correction ran.

## 8 · Superseded filings elsewhere in the repository

Skill files were filed in two other places before this folder existed. Both are superseded by pointer and neither is deleted, per the Prime Rule.

`skills/trisduction-audit-cycle/SKILL.md` is superseded by `protocols/subroutines/trisduction-audit-cycle_v1_0_0.md`.

`publication/SKILL_trisduction-publication-format_v1_1_0.md` through `_v1_3_0.md` are superseded by `protocols/subroutines/trisduction-publication-format_v1_0_0.md`, which carries the same bytes as `_v1_3_0`. The `publication/` folder keeps its label-map tooling, which is not a skill and stays where it is.

Both supersessions are recorded in `CODEX_DELETIONS.log`. A scribe resolving an instrument reads from this folder and treats the other two paths as history.

## 9 · Change discipline

A correction to an instrument is fixed at the instrument, not patched at the instance where it surfaced. A finding that extends an existing behaviour is an in-place revision of that skill at a bumped version, not a new skill, unless the finding is structurally distinct enough to stand alone. New skills are rare by design; the deck grows by instrument inside an existing file more often than by file.

This README is a pointer, not a census. Where the deck grows, the table in section 2 is updated in the same push that files the new instrument, and no separate bookkeeping is owed.
